# NTU Gym Tracker 提案

> 這裡只放**還沒定案**的提案。已實作的設計寫在 `docs/spec.md`，過程寫在 `docs/CHANGELOG.md`。
> 開始實作前請先讀 `docs/spec.md` 最上面的專案規則。

## 流程

1. 新想法寫成一節，狀態為「討論中」。
2. 討論後狀態改為「已同意」或「不做」：
   - **已同意**：把確定的設計寫進 `docs/spec.md`，再開始寫程式。
   - **不做**：從這裡刪掉；值得記住原因的話，加進 `docs/spec.md` 的「先不做的」。
3. 實作並試過之後，從這裡刪掉該節，過程記到 `docs/CHANGELOG.md`。

每節的格式：

```
## 標題
- 狀態：討論中 | 已同意
- 動機：為什麼要做
- 做法草案：打算怎麼做
- 待決定：還要確認的問題
```

## 平均與預測排除開/閉館的 0 標記

- 狀態：討論中
- 動機：`open` / `closed` 標記的人數是 0，被算進各時段平均，所以平均人數圖和預測線的第一格和最後一格永遠是 0，
  看起來像開館時沒人。
- 做法草案：`get_profile()` / `forecast_model` 的平均只用 `source_status == "ok"` 的列；圖表要歸零的話，
  在畫圖時另外補上頭尾的 0 點，而不是讓它進平均。
- 待決定：頭尾要不要畫 0？「今天的實際值」那條線要不要保留標記？

## 自動 push 到 GitHub

- 狀態：討論中
- 動機：`daily-check` 只 commit 不 push，GitHub 上的資料會越來越落後；工作站壞掉時異地備份就不完整。
- 做法草案：自動檢查 commit 後 `git push`；或另設每天一次的 cron 只做 push。
- 待決定：要不要讓自動流程有 push 權限？push 失敗（衝突、網路）時怎麼處理？

## 自動化測試

- 狀態：討論中
- 動機：解析器依賴網站的 HTML 結構，改版時會壞；目前只能靠 `parse_error` 事後發現。
- 做法草案：存幾份官網 HTML 當 fixture，測 `parser.py`；用 FastAPI `TestClient` 測各 API；
  `closures.py`、`daily_check.validate()` 也寫單元測試。
- 待決定：要不要用 `pytest`？要不要每次 commit 前自動跑？

## 異常通知

- 狀態：討論中
- 動機：連續 `fetch_error` / `parse_error`（網站掛掉或改版）、收集器停止，目前都要自己看網頁才會發現。
- 做法草案：`daily-check` 每次執行時順便檢查最近的資料，有異常就寫進 log 並用某種方式通知（例如 email、GitHub issue）。
- 待決定：通知管道？多久沒資料算異常？

## 計數器故障偵測

- 狀態：討論中
- 動機：現場計數器曾連續數天回報 0 而場館實際有開（見 `docs/spec.md` 注意事項），目前只能用眼睛發現。
- 做法草案：營業時間內某館整天的 `ok` 讀數都是 0（且當天沒有登記休館），就在 log / 通知中提醒，**不自動改資料**，
  由人工確認後再用 `csv-tool` 標成 `sensor_error`。
- 待決定：門檻（整天？連續幾小時？）；是否和「異常通知」合併。

## 機器學習預測

- 狀態：討論中
- 動機：`same_weekday_mean` 無法反映學期 / 寒暑假 / 考試週、前一個小時的人潮等因素。
- 做法草案：
  - 特徵：時段、星期、是否週末；學期週次、考試週、寒暑假、國定假日（需要學校行事曆，見下一節）；
    lag 特徵（前 1 小時、昨天同時段、上週同時段）。
  - 模型：先試 LightGBM 回歸，在 `forecast_model._STRATEGIES` 註冊成新策略。
  - 評估：MAE（平均差幾人），用「過去訓練、未來測試」的時間序列切分，不可隨機打散；
    要**贏過 `same_weekday_mean`** 才換成預設。
- 待決定：資料量門檻——星期效應至少要 3–4 週，學期效應要跨一整個學期；什麼時候開始做？

## 學校行事曆對照表

- 狀態：討論中
- 動機：機器學習預測需要「開學、考試週、寒暑假」等特徵，而這些不在休館名單裡（場館照常開）。
- 做法草案：手動維護 `data/academic_calendar.csv`（`date, end_date, kind`），`kind` 例如 `semester`、`exam`、`break`。
- 待決定：要不要也在網頁上顯示（例如行事曆標示考試週）？

## 短期預測（未來 1–3 小時）

- 狀態：討論中
- 動機：回答「現在出門的話到那邊擠不擠」，比整天的曲線更直接。
- 做法草案：用目前的人數和最近的趨勢修正基準線，在卡片上顯示「預計 1 小時後約 N 人」。
- 待決定：是否等機器學習預測完成再一起做？
